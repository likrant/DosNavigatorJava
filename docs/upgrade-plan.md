# План переноса Dos Navigator на Java

## Статус и цель

Этот документ является главным планом работ. Остальные `milestone-*.md` уточняют
отдельные области, но не могут ослаблять его требования.

Цель проекта - перенос Dos Navigator на Java с максимально близким внешним и
функциональным поведением, а не новый файловый менеджер в похожем стиле.
Приоритеты неизменны:

1. Поведение исходного Pascal-кода и ресурсов.
2. Клеточная разметка, тексты, атрибуты и состояния оригинального TUI.
3. Одинаковая работа Java-версии на Windows и Linux.
4. Внутреннее упрощение, рефакторинг и новые возможности - только после
   фиксации паритета.

Особенности и ограничения оригинала первоначально воспроизводятся. Изменить их
можно только отдельным продуктовым решением с тестом и документированным
отклонением.

## Источник истины

При конфликте источников применяется следующий порядок:

1. `DosNavigator-master`: Pascal units, `Commands.pas`, обработчики событий,
   `RESOURCE/*`, поставляемые конфигурации и документация.
2. Воспроизводимые результаты запуска старого DN в Windows Sandbox:
   `tests/legacy/ui-reference` и сценарии из
   `docs/legacy-dn-reference-test-plan.md`.
3. Автоматические Java-тесты и проверенные golden-артефакты.
4. Плановые документы и ручные наблюдения.

Скриншот не является единственным доказательством разметки: он подтверждает
визуальный вид, но не заменяет описания текстовой сетки, палитры и состояния.

## Обязательные контракты

### Соответствие исходникам

- Каждый переносимый Pascal unit получает явного Java-аналога или запись в
  реестре отклонений с причиной.
- Имена пакетов, классов, команд и основных методов сохраняют связь с
  исходниками. Новые общие абстракции допустимы только когда не скрывают
  исходную логику и имеют трассировку к Pascal-модулям.
- Для каждой команды фиксируются: Pascal id и имя, исходные обработчики,
  контексты, разрешенные и запрещенные состояния, эффект, ресурсные строки и
  все сочетания клавиш.
- Ни одна команда или ресурс, обнаруженные в исходниках, не могут оставаться
  в статусе `unknown`. Допустимые статусы: `implemented`,
  `compatible via adapter`, `unsupported by platform with substitute` или
  `removed by explicit decision`.

### Клавиатура и меню

- Весь набор клавиш из Pascal-кода, ресурсов меню, status line и keymap
  переносится в машиночитаемый каталог команд. Это включает F1-F12,
  Ctrl/Alt/Shift-варианты, серые клавиши, Insert/Delete, навигацию, Esc,
  Enter, Backspace и мнемоники.
- Тестируется не только соответствие клавиши command id, но и результат в
  каждом релевантном контексте: панели, верхнее меню, submenu, модальный
  диалог, viewer, editor и операции.
- Мнемоники являются языковыми ресурсами. Например, русская и английская
  цепочки меню могут иметь разные физические клавиши, но обязаны вести к
  одной команде. Тесты запускаются для каждого поддержанного языка.
- Поведение Esc и переходы по меню проверяются как цепочки состояний:
  `F10 -> mnemonic -> mnemonic -> Enter`, закрытие меню, подменю и формы.
  Нельзя заменять это проверкой одной только навигации стрелками.

### Разметка и цвет

Рендеринг обязан иметь платформенно-независимую модель кадра:

```text
Cell = glyph + foreground + background + attributes
Frame = width + height + ordered cells + cursor + active view
```

- Golden-артефакт хранится в UTF-8 JSON: размер сетки, каждый символ,
  псевдографика, координаты, цвета, атрибуты, курсор и активное состояние.
- Автотест сравнивает кадры на уровне `Cell`, а не по OCR и не только по PNG.
  Возможны явные маски для времени, размера окна и иных согласованно
  динамических полей.
- PNG создается из того же `Frame` только для просмотра человеком. Для
  эталонных форм используются данные `tests/legacy/ui-reference/screen-index.json`,
  декодированные ресурсы и проверенные Sandbox-снимки.
- Для каждого экрана тестируются минимум: границы и псевдографика, размеры и
  позиция окон, заголовки, подписи, hotkey-символы, selected/disabled/focused
  цвета и строки состояния.

### Кроссплатформенность

- Поддерживаемые целевые среды: Windows 11 и Linux x86_64 с JDK 21 и
  интерактивным ANSI-совместимым терминалом.
- Основная логика, каталог команд, ресурсы, layout engine и snapshot-тесты не
  используют Windows API, PowerShell или platform-specific пути.
- Файловая система, терминал, системные вызовы, принтер, сеть, архиваторы и
  legacy-device функции отделяются адаптерами. Каждый адаптер имеет Windows и
  Linux реализацию либо документированную замену.
- Тестовые фикстуры создаются через Java `Path` в temporary directory;
  разделители путей, кодировки, права доступа, case-sensitivity и drive roots
  проверяются отдельно.
- Любая функция, реализованная только для Windows, не считается завершенной
  без Linux-адаптера или явного platform status в реестре покрытия.

## Автоматическая стратегия проверки

### Наборы тестов

1. **Source coverage.** Генератор извлекает command/resource/keymap inventory
   из Pascal-кода и DNR/LNG/DLG. CI падает, если запись не имеет статуса,
   Java-реализации или одобренного исключения.
2. **Command tests.** Параметризованные тесты отправляют каждую
   зарегистрированную клавишу в каждое допустимое состояние и проверяют
   command id, состояние модели и отсутствие побочных действий вне фикстуры.
3. **Layout snapshots.** Headless `TestTerminalSurface` отрисовывает
   фиксированные размеры сетки и сравнивает JSON frame с golden-файлом.
4. **Behavior scenarios.** Скриптовые последовательности клавиш проверяют
   панели, меню, формы, file operations, viewer, editor, конфигурации и
   recovery. Файловые операции выполняются только в disposable fixture tree.
5. **Adapter integration.** На Windows и Linux проверяются реальные terminal
   input/output, filesystem, encoding, archive/process adapters и упаковка.
6. **Visual review.** PNG и отчеты публикуются как artifacts CI; расхождение
   по PNG само по себе не заменяет cell-level assertion.

### Требования к CI

- Матрица запускает `mvn test` на Windows и Ubuntu с JDK 21.
- Один и тот же проверочный набор не требует Windows Sandbox, PowerShell,
  GUI-сессии или OCR. Sandbox применяется только для пополнения legacy
  evidence на Windows.
- Проверки запускаются с `UTF-8`; отдельные тесты покрывают CP866 и другие
  унаследованные кодировки на границе импорта ресурсов.
- Golden-артефакты изменяются только в отдельном review с объяснением,
  ссылкой на Pascal source или новым legacy evidence.

## Порядок работ и контрольные точки

### Этап 0. Инвентаризация и тестовый фундамент

- Построить реестр `Pascal unit -> Java package/class -> tests -> status`.
- Сгенерировать полный каталог `Commands.pas`, menu/resource hotkeys и
  keymaps; добавить проверку полноты в Maven-тесты.
- Зафиксировать legacy UI reference: меню, панели, настройки, утилиты и
  последующие формы из изолированного DN.
- Утвердить JSON-схему Frame и golden fixtures для 80x25, 80x50 и размеров,
  необходимых эталонным экранам.

**Gate:** CI на Windows и Linux запускает source coverage, command catalog и
первый cell-level snapshot без GUI.

### Этап 1. TUI и событийная модель

- Перенести `views.pas`, `dialogs.pas`, `menus.pas`, `commands.pas`,
  `messages.pas`, `startup.pas`, `dn1.pas`, `dnapp.pas` с трассировкой к
  Java-классам.
- Реализовать retained-mode views, focus, z-order, modal loop, resize,
  menu/status line и базовые DN рамки/палитры.
- Ввести единый decoder input -> command -> state -> Frame.

**Gate:** все базовые клавиши и F10/Esc/menu mnemonic paths имеют сценарные
и layout-тесты; стартовый экран совпадает с golden grid на обеих ОС.

### Этап 2. Панели, каталоги и навигация

- Перенести `drives.pas`, `filescol.pas`, `flpanel.pas`, `flpanelx.pas`,
  `dblwnd.pas`, `xdblwnd.pas`, `fltools.pas`, `diskinfo.pas`.
- Реализовать две независимые панели, каталоги, сортировки, фильтры,
  выделения, brief/full view, быстрый поиск и panel status.
- Поведение локальных drive/path различий обеспечивается адаптерами, а не
  ветвлениями в UI-коде.

**Gate:** полный набор source-defined panel keys проверен на Windows и Linux;
snapshot покрывает active/passive/selection, колонки, parent/root и ошибки.

### Этап 3. Команды, меню, диалоги и настройки

- Перенести menu/resource loaders, setup dialogs, colors, histories и
  конфигурации из `setups.pas`, `colors*.pas`, `dnini*.pas`, `histries.pas`.
- Создать все формы из верхнего меню по ресурсной структуре и их cell-level
  контракты: позиция, рамка, элементы, текст, hotkeys и палитра.
- Отдельно реализовать языковые bindings для English/Russian/Ukrainian без
  привязки к текущей раскладке ОС.

**Gate:** каждая доступная ветка верхнего меню открывает соответствующую
форму в тесте; каждая форма сравнивается с golden grid и закрывается согласно
оригинальной Esc-семантике.

### Этап 4. Безопасные файловые операции

- Перенести `filecopy.pas`, `eraser.pas`, `filelst.pas`, `filetype.pas` и
  связанные диалоги/прогресс.
- Копирование, move, rename, mkdir, delete, маски, конфликты, отмена и
  обновление панелей проверяются на disposable fixture tree.

**Gate:** все branches команд и подтверждений воспроизводимы в обеих ОС,
включая ошибки прав/занятого файла там, где платформа их допускает.

### Этап 5. Viewer и editor

- Перенести viewer/editor units близко к исходнику, включая режимы, поиск,
  codepages, блоки, history, menus и status lines.
- Использовать эталонные файлы с кириллицей, binary data, large files и
  legacy encodings.

**Gate:** каждый режим имеет сценарий клавиш и cell-level snapshots на обеих
ОС; нет неучтенных key bindings.

### Этап 6. Архивы, поиск, tree, интеграции и утилиты

- Перенести archive/virtual panel modules, поиск, tree, user menu,
  calculator, calendar, ASCII table и остальные модули в порядке исходных
  зависимостей.
- Внешние программы и неуниверсальные устройства получают адаптеры либо
  документированную совместимую замену.

**Gate:** feature registry не содержит `unknown`; каждый adapter имеет
Windows/Linux тест или документированное исключение.

### Этап 7. Релизный паритет

- Проверить ресурсы, конфиги, миграцию, help, packaging и восстановление
  терминала после штатного выхода/ошибки.
- Выпустить coverage report, frame diff report и список осознанных отличий.

**Gate:** полный CI green на Windows и Linux; все команды, ресурсы и
сериализуемые legacy-состояния имеют подтвержденный статус.

## Definition of done

Релиз Java DN возможен только когда:

- для каждой команды и клавиши из исходников есть автоматический тест либо
  документированное исключение, утвержденное как продуктовое решение;
- все доступные меню и формы открываются через реальные hotkey/command paths,
  а не только через прямой вызов Java-кода;
- главные экраны сравниваются по текстовой сетке, цветам и состоянию, а PNG
  хранится как человекочитаемое доказательство;
- весь обязательный тестовый набор проходит на Windows и Linux;
- не остается неучтенных source/resource/behavior coverage gaps.
